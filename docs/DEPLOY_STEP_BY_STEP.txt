===============================================================================
  RAMACHANDRA TRADERS — STEP-BY-STEP DEPLOYMENT GUIDE
  GitHub push  ->  MongoDB Atlas  ->  Render  ->  Vercel
===============================================================================

  This is the checklist version: every step, every environment variable, every
  common error in one place. Follow it top to bottom.

  Companion files:
    docs/DEPLOY_GUIDE.txt          - the original reference guide
    docs/GOOGLE_SIGNIN_SETUP.txt   - Google OAuth console setup in full detail
    docs/AFTER_DEPLOY_CHECKLIST.txt

  Total time: about 60 minutes the first time. After that, updates take
  one command.


-------------------------------------------------------------------------------
  READ THIS FIRST — A COMMON MISUNDERSTANDING
-------------------------------------------------------------------------------

  "It's a Next.js project, so Vercel alone is enough."   <-- THIS IS WRONG.

  Vercel hosts ONLY the frontend. This is a full-stack application:

      Frontend (Next.js)  -> Vercel
      Backend  (Express)  -> Render
      Database (MongoDB)  -> MongoDB Atlas

  If you deploy only to Vercel, the site will open but nothing will work:
  no products, no login, no cart, no orders. There is no API behind it.

  All three services are required. All three are free.


-------------------------------------------------------------------------------
  OVERVIEW — THREE SERVICES
-------------------------------------------------------------------------------

  +---+------------------+------------------------------+-------+---------+
  | # | SERVICE          | WHAT IT HOSTS                | COST  | TIME    |
  +---+------------------+------------------------------+-------+---------+
  | 1 | MongoDB Atlas    | Database: products, orders,  | Free  | 10 min  |
  |   |                  | users, reviews               |       |         |
  +---+------------------+------------------------------+-------+---------+
  | 2 | Render           | Backend API (Express)        | Free  | 15 min  |
  +---+------------------+------------------------------+-------+---------+
  | 3 | Vercel           | Frontend storefront (Next.js)| Free  | 10 min  |
  +---+------------------+------------------------------+-------+---------+

  ORDER MATTERS: Atlas -> Render -> Vercel -> connect them together.

  Reason: the frontend needs the backend's URL, and the backend needs the
  frontend's URL. You cannot know either until each is deployed, so you deploy
  in this order and then go back and wire them together in PART 4.

===============================================================================
  PART 1 — MONGODB ATLAS (DATABASE)
===============================================================================

  +------+--------------------------------------------------------------------+
  | STEP | ACTION                                                             |
  +------+--------------------------------------------------------------------+
  |  1   | Go to https://www.mongodb.com/atlas and sign up (free)             |
  |  2   | Create a free M0 cluster. Pick the region closest to India         |
  |      | (Mumbai) for the lowest latency.                                   |
  |  3   | Database Access -> Add New Database User.                          |
  |      | Set a username and password. SAVE THE PASSWORD SOMEWHERE.          |
  |  4   | Network Access -> Add IP Address -> "Allow access from anywhere"   |
  |      | (0.0.0.0/0). Render's IP is dynamic, so this is required.          |
  |  5   | Database -> Connect -> Drivers -> copy the connection string       |
  +------+--------------------------------------------------------------------+


  FIX THE CONNECTION STRING BEFORE USING IT

  Atlas gives you a template that will NOT work as-is:

      mongodb+srv://myuser:<password>@cluster0.abcde.mongodb.net/?retryWrites=true

  You must make two edits — replace the password, and add the database name:

      mongodb+srv://myuser:RealPass123@cluster0.abcde.mongodb.net/ramachandra?retryWrites=true
                             ^^^^^^^^^^^                          ^^^^^^^^^^^^^
                             your real password                   database name


  +-----------------------------------+--------------------------------------+
  | COMMON MISTAKE                    | FIX                                  |
  +-----------------------------------+--------------------------------------+
  | Left <password> as literal text   | Replace it. Remove the < > brackets  |
  | Forgot the /ramachandra db name   | Add it right before the ? character  |
  | Password contains @ # / % : ?     | URL-encode it, or simply set a       |
  |                                   | password with letters + numbers only |
  +-----------------------------------+--------------------------------------+

  Save this final string. You will need it in PART 2.


===============================================================================
  PART 2 — RENDER (BACKEND API)
===============================================================================

  +------+--------------------------------------------------------------------+
  | STEP | ACTION                                                             |
  +------+--------------------------------------------------------------------+
  |  1   | Go to https://render.com and sign up WITH GITHUB                   |
  |  2   | Click "New +" -> "Blueprint"                                       |
  |  3   | Select the repository: laxtline/ramachandra-traders                |
  |  4   | Render automatically reads render.yaml from the repo root          |
  |  5   | Click "Apply"                                                      |
  +------+--------------------------------------------------------------------+

  Because render.yaml already exists, Render knows the root directory, build
  command, start command, and health check path. You do not configure those
  by hand.


  BACKEND ENVIRONMENT VARIABLES
  Render dashboard -> your service -> Environment

  +----------------------+------------------------------+--------------------+
  | VARIABLE             | VALUE                        | WHO SETS IT        |
  +----------------------+------------------------------+--------------------+
  | NODE_ENV             | production                   | AUTO (render.yaml) |
  | JWT_SECRET           | (random, auto-generated)     | AUTO (render.yaml) |
  | JWT_EXPIRES_IN       | 7d                           | AUTO (render.yaml) |
  | PORT                 | (leave blank)                | AUTO (Render)      |
  +----------------------+------------------------------+--------------------+
  | MONGODB_URI          | your Atlas string from PART 1| YOU — required     |
  | GOOGLE_CLIENT_ID     | copy from your local         | YOU — required     |
  |                      | Website/backend/.env         |                    |
  | CLIENT_ORIGIN        | LEAVE BLANK FOR NOW —        | YOU — in PART 4    |
  |                      | you don't know the Vercel    |                    |
  |                      | URL yet                      |                    |
  +----------------------+------------------------------+--------------------+
  | RAZORPAY_KEY_ID      | (leave empty)                | Optional           |
  | RAZORPAY_KEY_SECRET  | (leave empty)                | Optional           |
  | RESEND_API_KEY       | (leave empty)                | Optional           |
  | EMAIL_FROM           | (leave empty)                | Optional           |
  +----------------------+------------------------------+--------------------+

  The optional variables control feature flags. Leaving them empty simply
  disables online payment and order emails. The app works fully without them.


  AFTER THE DEPLOY FINISHES

  1. Copy your backend URL. It will look like:

         https://ramachandra-traders-api.onrender.com

  2. Test it — open this in a browser:

         https://ramachandra-traders-api.onrender.com/api/health

     Expected response:
         {"success":true,"data":{"status":"ok","uptime":12.34}}

     If you get an error instead, check the Render logs before continuing.
     Do not move to PART 3 until health check passes.


  SEED THE DATABASE (ONE TIME ONLY)

  The database is empty at this point. Load the branding and 72 demo products:

      Render dashboard -> your service -> "Shell" tab -> run:

          npm run seed

  Run this exactly once. Running it again will duplicate the demo data.


===============================================================================
  PART 3 — VERCEL (FRONTEND)
===============================================================================

  +------+--------------------------------------------------------------------+
  | STEP | ACTION                                                             |
  +------+--------------------------------------------------------------------+
  |  1   | Go to https://vercel.com and sign up WITH GITHUB                   |
  |  2   | Click "Add New" -> "Project"                                       |
  |  3   | Import the repository: laxtline/ramachandra-traders                |
  |  4   | *** Root Directory -> click "Edit" -> set to: Website/frontend *** |
  |  5   | Framework Preset: Next.js (auto-detected, leave it)                |
  |  6   | Add the environment variables listed below                         |
  |  7   | Click "Deploy"                                                     |
  +------+--------------------------------------------------------------------+


  *** STEP 4 IS THE SINGLE MOST COMMON DEPLOYMENT FAILURE ***

  This is a monorepo. The Next.js app is not at the repository root — it lives
  in Website/frontend. If you leave Root Directory at the default, Vercel looks
  for package.json at the root, does not find one, and the build fails with
  "No package.json found" or "No Next.js version detected".


  FRONTEND ENVIRONMENT VARIABLES
  Add these BEFORE clicking Deploy.

  +--------------------------------+----------------------------------------+
  | VARIABLE                       | VALUE                                  |
  +--------------------------------+----------------------------------------+
  | NEXT_PUBLIC_API_URL            | https://ramachandra-traders-api        |
  |                                |     .onrender.com                      |
  |                                | (your real Render URL from PART 2)     |
  +--------------------------------+----------------------------------------+
  | NEXT_PUBLIC_GOOGLE_CLIENT_ID   | copy from your local                   |
  |                                | Website/frontend/.env.local            |
  +--------------------------------+----------------------------------------+
  | NEXT_PUBLIC_SITE_URL           | https://your-app.vercel.app            |
  |                                | You don't know this yet — put any      |
  |                                | placeholder, then fix it in PART 4     |
  +--------------------------------+----------------------------------------+


  RULES FOR THESE VALUES

  +-------------------------------+------------------------------------------+
  | RULE                          | EXAMPLE                                  |
  +-------------------------------+------------------------------------------+
  | No trailing slash             | .../onrender.com/   WRONG                |
  |                               | .../onrender.com    RIGHT                |
  | Must be https, not http       | http://...onrender.com   WRONG           |
  | No path at the end            | .../onrender.com/api   WRONG             |
  +-------------------------------+------------------------------------------+


  IMPORTANT — HOW NEXT_PUBLIC_ VARIABLES WORK

  Any variable starting with NEXT_PUBLIC_ is baked into the JavaScript bundle
  at BUILD time, not read at run time. If you change one of these later, you
  MUST trigger a redeploy — otherwise the old value stays live even though the
  dashboard shows the new one.

      Vercel -> Deployments -> latest deployment -> "..." menu -> Redeploy

  Also note: NEXT_PUBLIC_ values are visible to anyone who opens the browser
  devtools. That is by design and is safe here — an API URL and a Google
  Client ID are not secrets. Never put a password or private key behind a
  NEXT_PUBLIC_ prefix.


===============================================================================
  PART 4 — CONNECT BACKEND AND FRONTEND  (CRITICAL STEP)
===============================================================================

  You now have both URLs. Go back and fill in the blanks you left earlier.

  +---------------+-------------------------+-------------------------------+
  | WHERE         | VARIABLE                | SET IT TO                     |
  +---------------+-------------------------+-------------------------------+
  | Render        | CLIENT_ORIGIN           | https://your-app.vercel.app   |
  | Vercel        | NEXT_PUBLIC_SITE_URL    | https://your-app.vercel.app   |
  +---------------+-------------------------+-------------------------------+

  No trailing slash on either. Then REDEPLOY BOTH services.

  What CLIENT_ORIGIN does: it is the CORS allow-list. The backend refuses
  browser requests from any origin not on this list. If it is blank or wrong,
  every API call from your live site fails with a CORS error.

  For multiple domains, use a comma-separated list with no spaces:

      CLIENT_ORIGIN=https://your-app.vercel.app,https://ramachandratraders.com


  ALSO UPDATE GOOGLE CLOUD CONSOLE

  +--------------------------------+----------------------------------------+
  | SETTING                        | ADD THIS VALUE                         |
  +--------------------------------+----------------------------------------+
  | Authorized JavaScript origins  | https://your-app.vercel.app            |
  | Authorized domains             | vercel.app                             |
  +--------------------------------+----------------------------------------+

  Full walkthrough with screenshots of every field:
      docs/GOOGLE_SIGNIN_SETUP.txt


  ABOUT CROSS-SITE COOKIES

  Your frontend (vercel.app) and backend (onrender.com) are on different
  domains, so the auth cookie is a cross-site cookie. The backend already
  handles this: in production it sets the cookie with Secure + SameSite=None.

  This only works when NODE_ENV=production is actually set on Render. If login
  appears to succeed but the user is immediately logged out, check that first.

  PART 6 — FUTURE UPDATES
===============================================================================

  Once the initial setup is done, deploying a change takes one command:

      git add .
      git commit -m "describe your change"
      git push origin main

  +-----------+--------------------------------------------+----------------+
  | SERVICE   | WHAT HAPPENS AUTOMATICALLY                 | TIME TO LIVE   |
  +-----------+--------------------------------------------+----------------+
  | Vercel    | Detects the push, rebuilds, goes live      | about 2 min    |
  | Render    | Detects the push, rebuilds, goes live      | about 5 min    |
  +-----------+--------------------------------------------+----------------+

  You do not need to touch either dashboard. Both watch the main branch.


  THE ONE EXCEPTION

  Environment variables are NOT deployed by git push. The .env files are in
  .gitignore and never leave your machine. If you add or change an environment
  variable, you must update it manually in the Render and/or Vercel dashboard
  and then redeploy that service.

===============================================================================
  THE TWO THINGS THAT BREAK MOST DEPLOYMENTS
===============================================================================

  1. VERCEL ROOT DIRECTORY

     Must be set to:  Website/frontend

     This is a monorepo. Vercel defaults to the repository root, finds no
     package.json there, and the build fails immediately.


  2. RENDER CLIENT_ORIGIN

     Must be your exact Vercel URL with NO trailing slash.

         https://your-app.vercel.app     RIGHT
         https://your-app.vercel.app/    WRONG — CORS will fail

     The backend compares this string character by character against the
     browser's Origin header. One extra slash and every API call is rejected.


  Get these two right and you have eliminated roughly 90 percent of the
  problems people hit when deploying this project.
